# Stored-Procedure Unit-Test Generator

`Generate-StoredProcTests.ps1` scans a directory of **T-SQL (SQL Server)** `.sql`
files that contain stored-procedure definitions and generates **C# xUnit** tests
that call each procedure through ADO.NET (`Microsoft.Data.SqlClient`).

For every `CREATE` / `ALTER` / `CREATE OR ALTER PROCEDURE` it finds, it emits a
`[Fact]` that:

- opens a `SqlConnection` (connection string comes from an environment variable —
  no secrets in the generated code),
- builds a `SqlCommand` with `CommandType.StoredProcedure`,
- adds every declared parameter with a type-appropriate sample value
  (`OUTPUT` parameters get `ParameterDirection.Output`; table-valued parameters
  get a `DataTable` placeholder with a `TODO`),
- runs the procedure inside a **transaction that is always rolled back**, so tests
  never mutate data,
- asserts the procedure executed without throwing (a *smoke test*), and leaves a
  `TODO` for real assertions on result sets / output parameters.

One test **class** is generated per input `.sql` file. If a file declares several
procedures, the class gets one `[Fact]` per procedure.

## Usage

```powershell
# Basic: scan a folder, write tests next to it
./Generate-StoredProcTests.ps1 -InputPath ./sql -OutputPath ./generated

# Full: standalone, buildable test project with a custom namespace + env var
./Generate-StoredProcTests.ps1 `
    -InputPath  ./sql `
    -OutputPath ./generated `
    -Namespace  MyApp.Db.Tests `
    -ConnectionEnvVar MYAPP_TEST_DB `
    -EmitProject `
    -Force
```

Requires PowerShell 7+ (`pwsh`). Works on Windows, Linux, and macOS.

### Parameters

| Parameter           | Required | Default                             | Purpose                                                                 |
| ------------------- | -------- | ----------------------------------- | ----------------------------------------------------------------------- |
| `-InputPath`        | yes      | —                                   | A directory (searched recursively) or a single `.sql` file to scan.     |
| `-OutputPath`       | yes      | —                                   | Directory for the generated `.cs` files (created if missing).           |
| `-Namespace`        | no       | `GeneratedTests.StoredProcedures`   | C# namespace for the generated classes.                                 |
| `-ConnectionEnvVar` | no       | `SP_TEST_CONNECTION`                | Env var the generated tests read the connection string from.            |
| `-EmitProject`      | no       | off                                 | Also emit a ready-to-build `.csproj` so the output is a standalone project. |
| `-Force`            | no       | off                                 | Overwrite existing generated files (otherwise they are skipped).        |

## Running the generated tests

The generated tests connect to a **real SQL Server** — point them at a
**disposable test database**, never production. The connection string is read
from the environment variable named by `-ConnectionEnvVar`:

```bash
# Linux / macOS
export SP_TEST_CONNECTION="Server=localhost;Database=MyApp_Test;Trusted_Connection=True;TrustServerCertificate=True;"
dotnet test
```

```powershell
# Windows (PowerShell)
$env:SP_TEST_CONNECTION = "Server=localhost;Database=MyApp_Test;Trusted_Connection=True;TrustServerCertificate=True;"
dotnet test
```

Every generated `[Fact]` is tagged `[Trait("Category", "StoredProcedure")]`, so you
can skip them until a database is available:

```bash
dotnet test --filter Category!=StoredProcedure
```

If you generated into an **existing** test project rather than using
`-EmitProject`, add the SqlClient package to that project:

```bash
dotnet add package Microsoft.Data.SqlClient
```

## What you get, and what you must fill in

The generator produces a **compilable smoke test** per procedure. It cannot know
your data, so treat the output as scaffolding:

- **Sample argument values** (`0`, `"test"`, `Guid.Empty`, …) are placeholders.
  Replace them with values that satisfy the procedure's foreign keys and business
  rules, or the smoke test may fail for legitimate reasons.
- **Table-valued parameters** are emitted as an empty `DataTable` with a `TODO` —
  add the columns and rows matching the SQL table type.
- **User-defined / unrecognized types** are emitted with a `TODO` and a `DBNull`
  (or `SqlDbType.Variant` for outputs) — set the correct type and value.
- **Assertions**: the scaffold only asserts the procedure ran. Add assertions on
  the returned result sets and output-parameter values for meaningful coverage.

Because generated files are marked `// <auto-generated>`, keep hand-written
assertions in a **separate partial class or file** so regenerating with `-Force`
doesn't discard them.

## What the parser handles

- `CREATE PROCEDURE`, `CREATE PROC`, `ALTER PROCEDURE`, `CREATE OR ALTER PROCEDURE`
- Schema-qualified and bracketed/quoted names (`[dbo].[usp_Foo]`, `dbo.Foo`, `Foo` → `dbo`)
- Parameter lists with or without wrapping parentheses
- Parameter defaults (`= 0`, `= NULL`, …), `OUTPUT` / `OUT`, and `READONLY` (TVPs)
- Types with length/precision (`NVARCHAR(MAX)`, `DECIMAL(18,2)`, `NUMERIC(10,4)`)
- `WITH RECOMPILE` / `FOR REPLICATION` option clauses (excluded from parameters)
- Comments (`--`, `/* */`) and string literals are stripped first, so `@` or the
  word `AS` inside them can't confuse detection

## Example

The [`samples/`](./samples) folder shows it end to end: the input procedures live
in [`samples/procs/`](./samples/procs) and the generated tests (committed for
reference) in [`samples/generated/`](./samples/generated). Regenerate them with:

```powershell
./Generate-StoredProcTests.ps1 -InputPath ./samples/procs -OutputPath ./samples/generated -EmitProject -Force
```
